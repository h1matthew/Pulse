[ACTION: Share screen. Open web/tsconfig.json and highlight line 7: "strict": true. Then open web/types/business.ts to show a TypeScript interface.]

For our programming language, we selected TypeScript version 5 with Strict Mode enabled. TypeScript is a statically-typed superset of JavaScript developed by Microsoft. We chose it over plain JavaScript specifically because strict mode enforces explicit type annotations on every variable, function parameter, and return value. This eliminates implicit any types entirely, which means an entire class of runtime errors — null reference exceptions, type mismatches, undefined property access — are caught at compile time rather than crashing in production. This is the same static analysis approach used by languages like Java and C-sharp, but within the JavaScript ecosystem so we can leverage Node.js, React, and the npm package registry.

As you can see here in our tsconfig, strict mode is enabled on line 7, and here is one of our typed interfaces defining the exact shape of a Business object.

[ACTION: Now open web/app/api/reviews/route.ts and scroll to the top to show the comment block.]

For our commenting standard, we developed a structured documentation format that is consistent across every file in our codebase. As you can see at the top of this API route for Reviews, every module opens with four labeled sections. USER JOURNEY describes the step-by-step path a request takes through this endpoint. INPUT VALIDATION is split into two subsections — Syntactical, which lists our Zod schema constraints like UUID format and character limits, and Semantic, which lists logical checks like duplicate review prevention and CAPTCHA verification. ACCESSIBILITY notes explain how error responses are structured for screen reader compatibility. And BOT PREVENTION documents our anti-spam measures. This is not boilerplate — each section contains specific, accurate details for that particular module.

SLIDE 4 — MODULAR PROGRAM
Rubric Row 3 (10 pts): Program is modular, logical, readable, shows advanced knowledge
================================================================================
SPEAKER: Matthew

[ACTION: Show VS Code with the web/ folder expanded in the sidebar. Point to each folder as you mention it. Then open web/app/layout.tsx to show the provider nesting: ThemeProvider > QueryProvider > AuthProvider > AccessibilityProvider.]

Our application is built on Next.js 16 with the App Router, Supabase PostgreSQL for our database, and deployed to Vercel for automatic CI/CD from our Git repository.

Let me show you how the codebase is organized. The app directory uses file-based routing — each page is its own folder with dedicated page, layout, loading, and error files. Components are split by feature — discover, dashboard, business detail — so each feature is completely self-contained. Hooks handle all data fetching. Lib holds utilities, validation schemas, and the report generator. Types defines our shared TypeScript interfaces.

Here in layout.tsx, you can see our provider architecture — ThemeProvider wraps QueryProvider wraps AuthProvider wraps AccessibilityProvider. Each provider has a single responsibility, and they nest in dependency order. This is a pattern used in large-scale React applications to separate concerns cleanly.

Our database has normalized tables for businesses, reviews, bookmarks, deals, check-ins, missions, and impact metrics, all connected through foreign key relationships with row-level security enforcing data access rules.

Pulse was designed with accessibility and usability as our top priorities. Let me cover our design principles — then Matthew will walk you through every feature live.

The user journey is: land on the homepage, discover businesses, engage through reviews and deals, and track your economic impact on the dashboard. No account is needed to browse — signing in unlocks engagement features. Matthew will show you this full flow in our demo.

For design rationale, we built mobile-first using Tailwind CSS with fluid breakpoints from 375 pixels on mobile to 1440 pixels on desktop. Card-based layouts let users scan quickly. Skeleton loaders match final card dimensions to eliminate layout shift during data fetching.

For accessibility, all interactive elements meet WCAG contrast thresholds. We support dark mode and light mode with a one-click toggle. The app is fully keyboard navigable — every action reachable via Tab and Enter. Screen readers receive announcements through aria-live regions when content updates. We implement skip-to-content links, focus traps for modals, and respect the user's prefers-reduced-motion operating system setting.

The interface is intuitive — buttons are labeled with icons and text, navigation is persistent in a fixed header, and interactive elements provide immediate visual feedback so the user always knows their current context.

SPEAKER: Felix (Input Validation)

[ACTION: Open web/app/api/reviews/route.ts in VS Code and scroll to the Zod schema section. Then scroll to the duplicate check code. Show the CODE only — do NOT demo the review form. Matthew demonstrates that live.]

We validate input on both levels the rubric specifies — syntactical and semantic. Let me show you the code.

Syntactical: we use Zod, a TypeScript schema validation library. Here is our createReviewSchema — it enforces that business_id is a valid UUID, rating is an integer 1 through 5, content is 10 to 2,000 characters, and photos is an array of valid URLs with a max of 5. If the format is wrong, the user gets a specific inline error saying exactly what needs to be fixed.

Semantic: we check whether the input makes logical sense. Here — if a user already reviewed this business, they get a 409 Conflict. CAPTCHA tokens are verified server-side — invalid tokens get a 400 rejection. The verified_purchase badge is auto-computed from check-in history so the user cannot fake it. On the login page, email format is checked syntactically, and Supabase validates semantically whether the credentials match a real account.

You will see both of these in action when Matthew demonstrates reviews and the CAPTCHA in our live demo.

FEATURE 3 — SORT BY REVIEWS AND RATINGS

[ACTION: Go back to Discover. Change the sort dropdown from Highest Rated to Most Reviewed, then to Nearest, then back to Highest Rated.]

The sort dropdown provides four options: Highest Rated, Most Reviewed, Nearest, and Name A through Z. Our default Highest Rated sort uses a weighted algorithm — the business rating multiplied by the logarithm base 10 of the review count. This means a 4.5-star business with 800 reviews ranks higher than a 5-star business with just one review, because the logarithm rewards credibility without letting massive chains dominate.

Download CSV generates a spreadsheet for Excel or Google Sheets. Print Report opens a clean print layout with white background, table borders, alternating row shading, and a Pulse footer. This is a professional, customizable, exportable report.


DATA STORAGE

[ACTION: Open Chrome DevTools with F12. Click the Application tab. Expand Local Storage. Click your site URL. Show the pulse-query-cache entry.]

For data storage, we use multiple levels. On the server, Supabase PostgreSQL stores businesses, reviews, bookmarks, deals, and impact metrics in normalized tables with foreign keys and row-level security.

On the client — here in DevTools — we persist React Query's cache to localStorage. This is the pulse-query-cache entry with a 24-hour time-to-live. The app loads instantly on return visits from this local cache, and React Query refreshes stale data in the background. We use typed arrays for photos and tags, structured objects for hours and metrics, and proper variable scoping throughout.
